## Context

当前视频在编辑器和列表中的显示依赖 media_kit Player 初始化，造成明显延迟。列表视图和瀑布流视图更是仅显示灰色占位符+播放图标，无法展示视频实际内容。图片通过直接文件读取实现即时显示，视频应达到同样体验。

现有架构：`VideoStorageService` 负责视频文件存储，`_VideoEmbedBuilder` 负责编辑器渲染，`MediaInfo` + `extractFirstMedia` 负责列表缩略图提取。所有组件已在生产环境中稳定运行。

## Goals / Non-Goals

**Goals:**
- 视频插入时预生成 JPEG 缩略图，编辑器和列表即时显示
- 编辑器中视频显示静态缩略图+播放按钮，点击后初始化播放器，降低资源占用
- 列表和瀑布流使用真实视频帧替代灰色占位符
- 向后兼容旧数据（无 thumbnail 字段时回退到现有行为）

**Non-Goals:**
- 不支持用户手动选择缩略图帧（使用默认第一帧或 seekMs=0）
- 不做缩略图定时刷新或视频内容变更后自动更新
- 不改变视频文件本身的存储逻辑
- 不处理视频截帧的进度显示（静默失败即可）

## Decisions

### 1. 截帧 API 选择：media_kit Player.screenshot()

**选择**: 使用已集成的 media_kit Player 的 `screenshot()` API
**替代方案**: ffmpeg 命令行工具
**理由**: 项目已依赖 media_kit，无需引入新依赖；screenshot API 返回原始 bytes，直接写入文件即可。ffmpeg 需要额外安装和平台适配。

### 2. 缩略图存储位置：与视频同目录

**选择**: `{appDir}/videos/{noteId}/thumb_{timestamp}.jpg`
**替代方案**: 独立的 `thumbnails/` 目录
**理由**: 与视频文件同目录便于生命周期管理——删除笔记视频目录时缩略图一并删除，无需额外清理逻辑。仅 `deleteVideo()` 需要增加删除缩略图的步骤。

### 3. 编辑器渲染策略：缩略图优先，按需初始化播放器

**选择**: 先显示静态缩略图图片+播放按钮覆盖层，用户点击后才创建 Player
**替代方案**: 直接显示 Player 但预热缓存
**理由**: 静态图片渲染零延迟、零资源占用。播放器创建和媒体初始化只在用户真正需要播放时发生，显著降低内存和 CPU 占用。

### 4. Delta JSON 格式扩展：增加可选 thumbnail 字段

**选择**: `{"source": "...", "width": 400, "thumbnail": "/path/to/thumb.jpg"}`
**替代方案**: 单独的 thumbnail 存储映射表
**理由**: 缩略图作为视频 embed 的一部分存储在 Delta 中，数据自包含，无需额外的查询和同步逻辑。向后兼容通过字段是否存在判断。

### 5. 截帧失败策略：静默回退，不阻塞插入

**选择**: 截帧失败时不写入 thumbnail 字段，视频照常插入
**替代方案**: 截帧失败时提示用户重试
**理由**: 截帧是优化体验的手段而非核心功能。对于网络视频或特殊编码格式，截帧可能失败，不应影响正常使用流程。

## Risks / Trade-offs

- **截帧耗时** → 视频插入流程变长（约 1-3 秒）。缓解：截帧在视频保存后异步执行，失败不阻塞。可在 UI 上显示简短 loading 指示。
- **缩略图文件占用额外存储** → 每个 JPEG 约 30-100KB，可忽略不计。
- **media_kit screenshot API 的平台兼容性** → Web 平台不支持 Player.screenshot()。缓解：Web 平台跳过缩略图生成，保持现有行为。
- **视频文件被外部修改后缩略图过时** → 接受过时风险，不自动更新。Non-Goal 中已排除。
